<objective>
Close the loop on D-06/D-07/D-09: an "Add to my empires" action on the selected empire in the Saved Empire
panel that converts any empire in the loaded `.sav` — player or AI — into a complete, correctly-named
design entry staged for the next save, with duplicate names disambiguated and the resulting name shown to
the user before they commit.

Purpose: this is the phase's headline capability; everything before it built the machinery.
Output: `stageAddFromEmpire` on the session, the panel action with its three states, staged-add rows in the
manager dialog, and a pure test for the staging logic.
</objective>

  <behavior>
    - `resolveStagedName(design.key, takenNames)` (the pure exported helper) returns the key unchanged when
      it is free, `"{key} (2)"` when the key is already in the file, and `"{key} (3)"` when both the key and
      its " (2)" form are taken.
    - Names already staged as adds count as taken, so adding the same empire's name twice yields distinct names.
    - The comparison is on raw strings: a taken name containing a 0x11 colour-escape byte does not collide
      with its code-stripped form.
    - Staging produces a `StagedAdd` whose `text` is the serialized entry, whose `rawName` is the resolved
      name, whose `originalName` is the pre-resolution key, and whose `sourceEmpireId` is the empire id.
    - The serialized text's own top-level entry name equals the RESOLVED name, not the original — the
      entry is serialized after the key is rewritten (assert with `findTopLevelSpans(text + separator)[0].name`).
    - Staging with no designs file loaded returns `{ staged: false, needsFile: true }` and adds nothing.
    - Staging an empire whose `design` is null returns `{ staged: false, needsFile: false }` and sets a
      user-facing error rather than throwing.
  </behavior>
  <action>
    Extend `app/src/lib/empire/useDesignsSession.ts`.

    Export a pure module-level helper `resolveStagedName(desiredKey: string, taken: readonly string[]): string`
    that simply delegates to `uniqueDesignName` (imported as a type-safe dynamic import is not possible for a
    pure helper — instead re-export a thin wrapper that the hook calls with the already-imported module, and
    keep the helper itself testable by taking the resolver as its inputs). Concretely: keep the disambiguation
    decision in one exported pure function that takes `(desiredKey, taken)` and returns the resolved name,
    implemented with the same " (N)" rule as `uniqueDesignName`, and have `designsText.ts`'s
    `uniqueDesignName` remain the single implementation the wrapper calls when the module is already loaded.
    Do not duplicate the numbering rule in two places — if the cleanest structure is to simply re-export
    `uniqueDesignName`, do that and make the test import it from here.

    Add the hook action:

    `stageAddFromEmpire(empire: SavedEmpire): Promise<{ staged: boolean; needsFile: boolean; rawName: string | null; renamedFrom: string | null }>`

    Behaviour:
    - When `designs` is null, return `{ staged: false, needsFile: true, rawName: null, renamedFrom: null }`
      immediately — the caller opens the manager dialog (UI-SPEC).
    - When `empire.design` is null, set `error` to a user-facing message explaining this empire cannot be
      converted to a design and return `{ staged: false, needsFile: false, ... }`. Never throw.
    - Otherwise: resolve the name against `takenNames` (which already includes the file's remaining raw names
      plus previously staged adds), build the entry as the design payload with `key` replaced by the resolved
      name, `await import("./designSerialize")` and serialize it with the loaded file's `separator` as the
      newline argument so the added text matches the file's own line endings, then call `stageAdd` with a
      `StagedAdd` whose `id` is `crypto.randomUUID()` when available and a counter-based fallback otherwise.
    - Re-staging the same `sourceEmpireId` replaces the existing staged add rather than creating a second one.
    - Return `renamedFrom` set to the original key when disambiguation changed the name, else null, so the
      UI can render the duplicate-name notice with real values.

    Then create `app/src/test/stageAdd.test.ts` covering the pure surface from the behavior block:
    the name-resolution rules (free / taken / taken-twice / staged-name-counts-as-taken / raw-byte
    comparison) and, by calling `serializeDesignEntry` directly with a rewritten key, the assertion that the
    serialized entry's top-level span name equals the resolved name. Build the `DesignEntry` fixture with the
    same factory style used in `designSerialize.test.ts`. Do not attempt to render the hook — this package has
    no jsdom and none is to be added.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| save-derived design payload → designs file | An AI empire's names, traits and flag ids originate in an untrusted save and become text in a real user data file |
| existing design identities | Overwriting an existing design's name would silently destroy a design the user built by hand |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-24 | Data loss | name collision on add | mitigate | `uniqueDesignName` disambiguates instead of overwriting (D-09), comparing raw bytes so a colour-coded name cannot alias onto another entry; the resolved name is shown to the user at stage time and is what gets serialized (asserted by the span-name test). |
| T-04-25 | Tampering | untrusted save strings entering file text | transfer | Sanitization lives in `serializeDesignEntry` (04-03, T-04-08); this plan must not build entry text by string concatenation anywhere — staging always calls the serializer. |
| T-04-26 | Tampering (rendered output) | staged-add names in the dialog and panel | mitigate | Rendered through `<PdxName>`; the filter uses the code-stripped display form while identity/collision logic uses raw bytes. No `dangerouslySetInnerHTML`. |
| T-04-27 | Repudiation | silent no-op when no file is loaded | mitigate | The action opens the manager dialog rather than failing quietly, so the user always sees why nothing was staged (UI-SPEC). |
| T-04-SC | Tampering | npm installs | mitigate | No packages installed. Any `npm install` during execution stops for human review. |
</threat_model>
