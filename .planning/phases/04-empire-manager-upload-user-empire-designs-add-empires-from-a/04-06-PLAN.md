<objective>
Complete the round trip: turn staged changes into the two output files (updated designs + archive of
removed designs), write them back in place where the File System Access API allows it — always after a
downloaded backup — and fall back to plain downloads everywhere else.

Purpose: this is where D-05 ("removal is never destructive-only"), D-08 (splice, never re-serialize) and
D-02 (backup before in-place write) become observable behaviour rather than library capabilities.
Output: `buildOutputs`/`save` on the session, the dialog's save/discard/replace confirmations and result
banners, and a pure test for output construction.
</objective>

    - `buildDesignsOutputs(designs, archive, removed, adds)` (the pure exported core) returns the updated
      designs text, the archive text or null, and the added/removed counts.
    - Zero staged changes: the designs output text equals the original file text exactly.
    - One removal: the designs output omits exactly that entry's bytes and every other entry's bytes are
      byte-identical to their original slices; the archive output contains exactly the removed entry's text
      followed by the separator.
    - Removals with an uploaded archive: the archive output starts with the uploaded archive's original text
      unchanged (byte-prefix assertion) and the removed entries are appended after it.
    - Removals with NO uploaded archive: the archive output is exactly the removed entry texts joined by the
      separator plus a trailing separator — no leading separator, no synthesized header.
    - Zero removals: the archive output is null (nothing is emitted for an adds-only save).
    - Adds: added entry texts appear after all kept entries in the designs output, in staging order.

  <action>
    Extend `app/src/lib/empire/useDesignsSession.ts`.

    First add `designsOriginalBytes: Uint8Array | null` to the session state, set in both `loadDesignsFile`
    and `loadDesignsViaPicker` from the exact bytes that were read. This is what the pre-write backup uses —
    re-encoding `designs.text` is NOT acceptable, because a file that fell back to the windows-1252 decode
    path would not re-encode to the same bytes.

    Export a PURE function (module-level, outside the hook, so it is unit-testable in the node environment):

    `buildDesignsOutputs(designs: DesignsFile, archive: DesignsFile | null, removed: ReadonlySet<number>, adds: readonly StagedAdd[]): { designsText: string; archiveText: string | null; addedCount: number; removedCount: number }`

    Implementation: `designsText = spliceDesignsFile(designs, removed, adds.map(a => a.text))`. For the
    archive, collect the removed entries' original texts as `designs.text.slice(entry.start, entry.end)` in
    file order. When `removed.size === 0`, `archiveText` is null. Otherwise, when an archive file was
    uploaded, `archiveText = spliceDesignsFile(archive, new Set(), removedTexts)` — the same splice engine, so
    previously-archived entries are never re-serialized (D-08's "same rule for the uploaded archive file",
    RESEARCH Pitfall 6). When no archive was uploaded, build a synthetic empty `DesignsFile`-shaped object
    (`text: ""`, `entries: []`, `separator` copied from the designs file, `filename` set to the D-04 default
    `user_empire_designs_archive.txt`) and run it through the identical `spliceDesignsFile` call so there is
    exactly one output-construction code path.

    Then add to the hook:

    `save(): Promise<void>` — no-op when `pendingCount === 0`. Otherwise:
    (1) call `buildDesignsOutputs` and encode both texts with `encodeDesignsText`;
    (2) if `handle` is set, re-check `await ensureReadWritePermission(handle)` (permission is not guaranteed
    to persist) and on success call `saveInPlaceWithBackup(handle, designsOriginalBytes, designsBytes, designs.filename)`,
    capturing the returned `backupName`; on a false result or any thrown error, set `error` to the UI-SPEC
    permission-denied copy and continue to the download path rather than aborting;
    (3) otherwise (or after that fallback) `downloadBlob(designsBytes, designs.filename)` — the SAME filename
    the user uploaded, never a reconstructed or version-suffixed name (D-03);
    (4) whenever `archiveText` is non-null, `downloadBlob(archiveBytes, archive?.filename ?? "user_empire_designs_archive.txt")`.
    The archive is always a download even in the in-place path — D-02 scopes File System Access write-back to
    the primary designs file only;
    (5) on success set `lastSave: { added: number; removed: number; backupName: string | null }` on the session,
    clear `removed` and `adds`, and re-baseline by parsing the new designs bytes through `parseDesignsFile`
    (dynamic import, same as the load path) and replacing `designs` and `designsOriginalBytes` with the
    result — otherwise the stored spans would be stale and a second save in the same session would splice
    from the wrong offsets;
    (6) expose `lastSave: { added, removed, backupName } | null` and a `clearLastSave()` action so the dialog
    can render and then dismiss the success banner.

    All parser access stays behind `await import("./designsText")` inside the handler.

    Then create `app/src/test/designsOutputs.test.ts` covering every bullet of the behavior block against
    `buildDesignsOutputs` with inline CRLF fixtures built the same way as `designsText.test.ts` (construct the
    `DesignsFile` objects by running the fixture text through `parseDesignsFile`, so spans are real).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app memory → user's real designs file | `createWritable()`/`close()` overwrites real user data with no undo |
| app memory → archive file | The archive is the sole recovery path for a removed design (D-05) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-19 | Repudiation / data loss | in-place write path in `save()` | mitigate | The write goes exclusively through `saveInPlaceWithBackup` (04-02), whose first statement is the backup download, using the stored ORIGINAL bytes rather than a re-encode. The UI has no path that writes in place without that call. |
| T-04-20 | Data loss | removal without archive | mitigate | `buildDesignsOutputs` derives the archive from the same removed-index set that drives the designs splice, so a removal cannot exist without a corresponding archive entry (D-05); asserted by the removal test pairing both outputs. |
| T-04-21 | Tampering | archive re-serialization | mitigate | The uploaded archive is spliced with the identical `spliceDesignsFile` engine and an empty removal set, so its existing bytes are copied verbatim; asserted by the byte-prefix test (RESEARCH Pitfall 6). |
| T-04-22 | Tampering | stale spans after a save | mitigate | `save()` re-parses the emitted bytes and replaces `designs`/`designsOriginalBytes`, so a second save in the same session splices from correct offsets instead of the pre-save index map. |
| T-04-23 | Denial of service (UX dead end) | permission revoked between upload and save | mitigate | `ensureReadWritePermission` is re-checked at save time; a false result or thrown error sets the UI-SPEC permission-denied copy and continues to the download path (D-02: never require the API). |
| T-04-SC | Tampering | npm installs | mitigate | No packages installed. Any `npm install` during execution stops for human review. |
</threat_model>
