# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (deliberate — matches Phase 2's locked rationale, see below) |
| Preset | not applicable |
| Component library | none — hand-built, extends the existing dark-chrome DOM component set (`EmpirePanel`, `TechDetailPanel`, `WhatsNew`, `FindOverlay`) |
| Icon library | none — reuses the app's existing unicode glyph vocabulary (✕ close, ▸/▾ collapse, ↗ jump, ✓ confirm) and the pipeline's already-generated `_<id>.webp` metadata icons (`auth_*`, `origin_*`, `civic_*`, `ethic_*`) for design-row badges. No new asset pipeline work — the design file's `empire_flag`/species portrait art is NOT rendered (no such icon set exists in the pipeline output); rows use text only for those fields. |
| Font | System UI stack — `--font-sans` (unchanged); filenames/timestamps use `--font-mono, monospace` at 12px, matching the existing `.app-header__version` chip precedent |

### Design System Rationale

`components.json` still does not exist (confirmed — unchanged since Phase 2). No shadcn gate fires here for the same reasons Phase 2 documented: `tokens.css` is the single source of theme truth (D-11/UIFX-01, still governing), and this phase's UI surface (an upload zone, a scrollable list, a staged-changes dialog, a save-confirmation flow) is well within reach of the app's existing hand-rolled dialog/panel/list patterns (`.whats-new`, `.find-overlay`, `.empire-settings`, `.empire-panel`). Introducing shadcn now would mean running two parallel component/theming systems for one CRUD-ish surface — not worth it. **Overriding constraint for this phase (per task brief): visual consistency with the existing app beats any abstract "best practice" component choice.** Every pattern below is a direct extension of an existing, shipped component — not a new visual language.

Registry safety gate: not applicable (no shadcn, no registries).

## Spacing Scale

Declared values (multiples of 4, 8-point scale) — unchanged from Phase 2, reused as-is:

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| `--space-xs` | 4px | Chip/badge internal padding, icon-to-text gaps in design-row metadata |
| `--space-sm` | 8px | List row internal padding, gap between stacked form controls |
| `--space-md` | 16px | Dialog body padding, gap between major sections (upload / list / pending-changes) |
| `--space-lg` | 24px | Dialog header/footer padding, empty-state card padding |
| `--space-xl` | 32px | Space between dialog edge and backdrop on wide viewports |
| `--space-2xl` | 48px | Not used this phase (declared for continuity) |
| `--space-3xl` | 64px | Not used this phase (declared for continuity) |

Exceptions (both are pre-existing app conventions, not introduced by this phase):
- Pill/badge padding below 4px (e.g. `2px 7px` on `.empire-chip`) — reused verbatim for the "in-place saving enabled" / "download only" file-mode badge and the "Added from save" pending-add badge.
- List-row meta text (authority/species line under a design name) uses tight 2-4px internal gaps, matching `.find-box__result`'s existing layout.

## Color

Reuses the app's actual shipped dark-chrome palette (the `--tree-*` tokens), **not** the lighter `:root` `--color-bg`/`--color-surface` pair that `tokens.css`'s comments describe as the aspirational default — in practice, every docked/floating chrome surface in this app (header, `.empire-panel`, `.empire-settings`, `.find-overlay`, `.whats-new`) already renders on the dark tokens. This phase follows the app as it actually ships, per the "match existing visual language" constraint.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--tree-panel` (`#1a2130`) | Dialog background, list-row default background, upload-zone background |
| Secondary (30%) | `--tree-bg` (`#10141c`) | Backdrop behind the dialog, nested/inset strips (pending-changes summary bar, filename/timestamp chips) |
| Accent (10%) | `--color-select` (`#ffd23f`, gold) | Reserved for: drop-zone hover border, search/filter input focus border, active "View pending changes" toggle state, list-row hover background tint, duplicate-name notice icon/text |
| Destructive | `--color-danger` (`#b91c1c`) | Reserved for: Remove-button hover/focus state only (not its resting state — see Removal & Archive Flow below), inline parse-error text, permission-denied error text |

**Primary CTA color note:** the app has exactly one existing precedent for a filled primary-action button — `.overlay__retry-button`, which uses `--color-accent` (`#2563eb`, blue) on `--color-surface` text. The "Save changes" button in this phase reuses that exact precedent (blue fill, not gold) so the app has one consistent "this button commits an action" color, distinct from gold's "this is currently selected/hovered" role. Positive/success confirmation (post-save banner, "Added ✓" state) uses `--color-good` (`#57c96a`, green) — the same green already used for the "researched" bucket in `EmpirePanel`, so "green = good outcome" stays consistent app-wide.

Accent reserved for: hover/focus/active interaction states and the duplicate-name notice only. Never used for the primary CTA fill (blue owns that), never used for destructive actions (red owns that).

### Dialog Close Behavior (exception to `.whats-new`'s pattern)

`.whats-new` and `.find-overlay` both close on backdrop click / ✕ with zero cost (nothing is lost). This dialog is different: closing it with unsaved staged adds/removes must not feel like data loss. Backdrop-click and ✕ both close the dialog, but staged changes persist in memory and re-open with the dialog (the pending-changes badge on the entry-point button, described above, is what signals this). "Discard changes" in the footer is the only action that actually clears staged state, and it requires the confirmation described in Removal & Archive Flow below only if there are staged removals pending (adds-only discards need no confirmation — nothing external is affected).

## Upload & File State

| State | Spec |
|-------|------|
| No file loaded (initial) | Drop-zone, visually and behaviorally identical to the existing `.empire-drop` component: dashed `1.5px` border in `--tree-border`, `border-radius: 8px`, `--space-md`-ish padding, hover → border color `--color-select`. Copy: **"Drop your empire designs file here or click to choose"** with the literal example filename shown as inline `<code>` text in muted gold, e.g. `user_empire_designs_v3.4.txt` — illustrative only, per D-03 the app accepts whatever filename the user provides and never hardcodes the version suffix in actual matching logic. |
| File picker mode | Feature-detect `showOpenFilePicker` (D-02): if available, the same click target invokes it (enabling in-place write-back for this session); if not, a plain `<input type="file" accept=".txt">` is used. No separate visible button for the two paths — one drop-zone, silently better-enabled in supporting browsers, per D-02's "never require the API" instruction. |
| Parsing | While `jomini.parseText` + span-scan run: drop-zone/loaded-file-row shows the same in-place "Parsing…" text substitution already used for the sample-save button in `EmpirePanel` (disabled state, no spinner needed for a sub-second parse). |
| Loaded (success) | Drop-zone is replaced by a compact "loaded file" row: filename (`var(--font-mono, monospace)`, 12px) + a file-mode badge + a small "change file" text link (re-opens the picker; loading a new file replaces the current session's list and clears staged changes — see Copywriting Contract for the confirmation text this requires if changes are pending). |
| File-mode badge | Pill badge, same visual construction as `.empire-chip` (rounded, bordered, small colored dot). Two variants: **"In-place saving enabled"** (green dot, `--color-good`) when a `FileSystemFileHandle` with write permission is active; **"Download only"** (neutral dot, `--tree-border`-colored) when falling back to Blob/`a[download]`. This is informational only — never blocks the flow. |
| Loaded (error) | Drop-zone stays, gains an inline error line directly below it in the same style as `.empire-panel__error` (12px, `#ff6b7a`/`--color-danger`-family text, no icon). Copy in Copywriting Contract below. The drop-zone remains interactive (re-drop/re-click) — no separate "retry" button needed since re-selecting a file IS the retry action. |

## Archive Upload (optional, secondary)

Collapsed by default behind a plain text toggle beneath the primary upload zone — this is optional per D-04, and should visually read as "not required," not compete with the primary flow:

| Property | Spec |
|----------|------|
| Collapsed state | Text button, no border/background, `--color-select` text on hover only: **"+ Add an existing archive file (optional)"** |
| Expanded state | Reveals a smaller drop-zone (same `.empire-drop` visual treatment, reduced padding) with copy: **"Drop your existing `user_empire_designs_archive.txt` here to keep appending to it"**. If skipped, a fresh archive is generated on save (per D-04) — no error state needed for "no archive uploaded," that's the default, expected path. |
| Loaded archive | Same compact "loaded file" row pattern as the primary upload, minus the file-mode badge (the archive file is only ever written via download, never in-place — D-02's FS-Access write-back is scoped to the primary designs file only per CONTEXT.md; keep the archive path simple). |

## Pending Changes Summary

A visually distinct strip inside the dialog body (between the list and the footer), using the "secondary" surface token so it reads as a summary rather than another list:

| Property | Spec |
|----------|------|
| Background | `--tree-bg` (the darker "secondary" token — see Color), `border-radius: 6px`, `--space-sm` `--space-md` padding — visually recessed relative to the `--tree-panel` dialog body, signaling "this is a summary of what's above, not new content" |
| Content (0 pending) | Not rendered at all — no empty strip taking up space when there's nothing to summarize |
| Content (>0 pending) | **"{N} pending change{s}: {A} added, {R} removed"** — plain text, 14px, `--tree-text`. If R > 0, append: **"Removed designs are archived, not deleted."** in the 12px muted caption style, directly under the count line, so the non-destructive nature of removal is visible every time changes are staged, not just at the final confirm step. |

## Save / Download Outcome Flow

This is the phase's one genuinely destructive-adjacent moment (an in-place file write) — copy and sequencing below implement D-02's mandatory pre-write backup and D-05's "never destructive-only" guarantee.

| Step | Spec |
|------|------|
| Trigger | "Save changes" button in the dialog footer — primary blue (`--color-accent`) fill, disabled (reduced opacity, no pointer events) when 0 pending changes exist |
| Confirmation (only shown if pending removals > 0, or if writing in-place) | A lightweight inline confirmation replaces the footer's action row (not a second modal-on-modal — stay within the same dialog, matching the app's existing "no nested dialogs" convention). Copy varies by write mode — see Copywriting Contract. Two buttons: **"Cancel"** (ghost) and **"Save & continue"** (primary blue, matches Save changes styling) |
| In-place write path | Backup (`Blob` + `a[download]`) fires first, then `createWritable()`/`write()`/`close()` — this ordering is a correctness requirement (RESEARCH.md Pattern 5), not just a UI nicety; the UI must not let the user skip past the backup step, so it is emitted automatically as part of clicking "Save & continue," with no separate "download backup" button the user could decline |
| Download-only path (no FS Access / non-Chromium) | Two file downloads fire directly (updated designs file + archive file, only if removals occurred): no separate confirmation screen needed beyond the removal-count confirmation above, since nothing on the user's disk is touched automatically |
| Success | Inline success banner replaces the pending-changes summary strip, `--color-good` green left-border accent (~3px, matching `.overlay__card--danger`'s left-border-accent construction but in green), auto-dismissing is NOT used (per app convention overlays/panels stay until explicitly closed) — copy in Copywriting Contract |
| Failure (permission denied mid-write) | Falls back automatically to the download-only path per D-02 (never leaves the user stuck) — inline error text in `--color-danger`, then the downloads fire immediately after. Copy in Copywriting Contract. |
| Failure (malformed source file, jomini/span-scanner can't reconcile) | Caught at upload time (Upload & File State's "Loaded (error)" row), never reaches the Save step — "Save changes" is simply unavailable until a file parses cleanly. |
